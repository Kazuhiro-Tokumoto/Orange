## 1. 概要

**Orange** (記号: **OAG**) は、RandomX を Proof of Work に用いる CPU マイニング型の
UTXO ブロックチェーンである。

| 項目 | 内容 |
| --- | --- |
| 合意形成 | Proof of Work (RandomX) |
| 会計モデル | UTXO |
| プライバシー | なし (透明台帳) |
| 署名 | Schnorr / BIP340 (secp256k1) |
| ブロック間隔 | 60 秒 |
| 総発行量 | 1,000,000,000 OAG |
| 初期配布 | **なし** (全量マイニングによって発行) |
| 実装言語 | Rust |

### 設計目標

1. **公平な分配** — プレマイン・ICO・開発者報酬を一切持たない。RandomX の CPU 最適化
   により、専用ハードウェアを持たない参加者でも採掘に参加できる。
2. **単純さ** — スクリプト言語も仮想マシンも持たない。検証すべきものは署名と金額の
   帳尻のみ。攻撃面を最小に保つ。
3. **長期的な分配** — 半減期を持たない線形発行により、190 年にわたって新規参加者に
   採掘機会が残る。

### 明示的な非目標

- **プライバシー** — 本チェーンは透明台帳である。すべての取引額と取引の関連は
  公開され、チェーン分析が可能である。Monero 等のプライバシーコインではない。
- **スマートコントラクト** — 任意計算の実行環境を持たない。AMM 型 DEX、レンディング、
  デリバティブ等は本チェーン上では実現できない。
- **高スループット** — 約 17 tx/秒。決済ネットワークの置き換えを目的としない。

## 2. 表記と用語

- `u8`, `u32`, `u64`, `u128`, `i64` — 固定幅の符号なし / 符号付き整数。すべて
  リトルエンディアンでシリアライズする。
- `varint` — LEB128 可変長整数。7 ビットずつ格納し、最上位ビットが継続を示す。
- `atomic` — OAG の最小単位。1 OAG = 10^16 atomic。
- `[u8; N]` — 長さ N の固定長バイト列。
- **MUST / MUST NOT / SHOULD** — RFC 2119 に準ずる。

すべてのハッシュ値・鍵・署名は、16 進表記する際にビッグエンディアン
(バイト列の先頭が左) で記す。

## 3. 通貨単位

```
1 OAG = 10,000,000,000,000,000 atomic   (10^16)
小数桁数 = 16
```

### 金額型

金額は **`u128`** で表現する。

```
総発行量 (atomic) = 1,000,000,000 × 10^16 = 10^25
u128 の最大値                             ≈ 3.40 × 10^38
```

`u64` (最大約 1.84 × 10^19) では表現できないため、`u128` を用いる。

### 実装上の必須要件

金額の算術は、コンセンサスに関わるすべての経路で以下を MUST とする。

1. **`Amount` を newtype で定義し、内部の `u128` を外部に露出しない。**

   ```rust
   pub struct Amount(u128);
   ```

2. **加算・減算・乗算はすべて `checked_*` を用いる。** オーバーフローが発生した場合、
   `None` を「無効なトランザクション」として扱う。

3. **`panic!` してはならない。** 攻撃者が任意のノードを停止できる DoS になる。
   オーバーフローは常に検証エラーとして扱う。

4. **すべての金額に範囲チェックを適用する。**

   ```
   0 ≤ amount ≤ MAX_SUPPLY  (= 10^25)
   ```

   この制約により、ブロック内の金額合計は数学的に `u128` を溢れない。
   200,000 バイトのブロックに入る出力数の上限は約 4,700 であり、
   `4,700 × 10^25 ≈ 4.7 × 10^28 ≪ 3.4 × 10^38` であるため。

5. **`Cargo.toml` の release プロファイルでも `overflow-checks = true` を有効にする。**
   静かに誤った金額を生成するより、異常終了する方が被害が小さい。

6. **RPC / JSON では金額を文字列として表現する MUST。**
   JavaScript の `Number` は 2^53 までしか正確に表現できず、
   atomic 単位の金額は容易にこれを超える。

> **背景**: Bitcoin は 2010 年 8 月、ブロック 74638 において整数オーバーフローにより
> 1,844 億 BTC を生成する事故を起こした (CVE-2010-5139)。出力金額の合計が `int64` を
> 溢れて負値に回り込み、「入力 ≥ 出力」の検証を通過したことが原因である。
> 本仕様の上記 1〜4 はこの事故の再発を構造的に防ぐためのものである。

## 4. 発行スケジュール

### パラメータ

```
BLOCK_REWARD          = 10 OAG = 10^17 atomic     (固定・不変)
MAX_SUPPLY            = 1,000,000,000 OAG = 10^25 atomic
EMISSION_END_HEIGHT   = 100,000,000
PREMINE               = 0
```

### 報酬関数

```
block_subsidy(height) =
    10 OAG   if height < 100,000,000
    0        otherwise
```

半減期は存在しない。報酬は発行終了高さまで一定である。

### 発行完了までの時間

```
100,000,000 ブロック × 60 秒 = 6,000,000,000 秒
                             ≈ 190 年 3 ヶ月
```

### 供給曲線

| 経過年 | 流通量 (OAG) | 総発行比 | 年間インフレ率 |
| ---: | ---: | ---: | ---: |
| 1 | 5,256,000 | 0.53 % | — |
| 2 | 10,512,000 | 1.05 % | 100.0 % |
| 3 | 15,768,000 | 1.58 % | 50.0 % |
| 5 | 26,280,000 | 2.63 % | 25.0 % |
| 10 | 52,560,000 | 5.26 % | 11.1 % |
| 20 | 105,120,000 | 10.51 % | 5.3 % |
| 50 | 262,800,000 | 26.28 % | 2.0 % |
| 100 | 525,600,000 | 52.56 % | 1.0 % |
| 190.3 | 1,000,000,000 | 100.00 % | 0 |

年間インフレ率は `1 / 経過年数` に従って減衰する (線形発行の数学的性質)。

### コインベーストランザクション

各ブロックはちょうど 1 個のコインベーストランザクションを含む MUST。

```
coinbase_output_total ≤ block_subsidy(height) + Σ(そのブロックの取引手数料)
```

不等号であることに注意。マイナーは報酬の一部または全部を放棄できる
(放棄された分は永久に発行されない)。

コインベース出力は **120 ブロック** が経過するまで使用できない
([コインベース成熟](#10-コンセンサスルール))。

## 5. 暗号プリミティブ

### 5.1 汎用ハッシュ関数: BLAKE3

トランザクション ID、マークルツリー、ブロックハッシュ、その他プロトコル内の
すべての汎用ハッシュには **BLAKE3** (256 ビット出力) を用いる。

```
H(x) = BLAKE3(x)[0..32]
```

BLAKE3 は長さ拡張攻撃に対して構造的に耐性があるため、Bitcoin のような
二重ハッシュ (`SHA256(SHA256(x))`) は不要である。

**ドメイン分離**: 用途ごとに異なるプレフィックスを付す。

```
txid          = H(0x00 || tx_serialized)
merkle_leaf   = H(0x01 || txid)
merkle_node   = H(0x02 || left || right)
block_hash    = H(0x03 || header_serialized)
```

用途が増える場面 (sighash など) では、1 バイトの識別子ではなく文字列タグを
用いる。[§8.0](#80-タグ付きハッシュ) を参照。

### 5.2 楕円曲線: secp256k1

```
p = 2^256 - 2^32 - 977
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
G = (0x79BE667EF9DCBBAC55A06295CE870B07029BFCDB2DCE28D959F2815B16F81798,
     0x483ADA7726A3C4655DA4FBFC0E1108A8FD17B448A68554199C47D08FFB10D4B8)
```

秘密鍵 `d` は `1 ≤ d < n` を満たす MUST。

### 5.3 署名: Schnorr (BIP340)

**BIP340 に完全準拠する。**

- 公開鍵は **x-only 32 バイト**。Y 座標は偶数であるものと暗黙に定める。
- 署名は **64 バイト固定** (`r: 32 || s: 32`)。
- 内部のタグ付きハッシュは BIP340 の規定通り **SHA-256** を用いる
  (BLAKE3 ではない。これは BIP340 の仕様であり変更しない)。

  ```
  tagged_hash(tag, msg) = SHA256(SHA256(tag) || SHA256(tag) || msg)
  タグ: "BIP0340/challenge", "BIP0340/aux", "BIP0340/nonce"
  ```

- ノンス生成は BIP340 の補助乱数付き決定的方式に従う SHOULD。

**バッチ検証**: 実装は 1 ブロック内の全署名をバッチ検証する SHOULD。
個別検証比で約 2 倍高速であり、60 秒ブロック間隔において有意である。

**展性がないこと**: BIP340 署名は固定長かつ厳密な符号化を持ち、
本チェーンはスクリプトを持たない。したがって**第三者はトランザクション ID を
書き換えられない**。この性質により、SegWit 相当の機構を持たずとも
事前署名トランザクション (アトミックスワップの返金経路等) が安全に成立する。

### 5.4 マークルツリー

**RFC 6962 (Certificate Transparency) 方式**を採用する。

```
MTH([])        = H(0x01 || 空)                      // 空ブロックは存在しないため未使用
MTH([d0])      = merkle_leaf(d0)
MTH(D[0..n])   = merkle_node(MTH(D[0..k]), MTH(D[k..n]))
                 ただし k は n 未満の最大の 2 冪
```

葉と内部ノードに異なるドメイン分離プレフィックスを用い、
奇数ノードの複製を行わない。

> **背景**: Bitcoin のマークルツリーは奇数ノードを複製して埋める設計のため、
> 異なるトランザクション列から同一のマークルルートを構成できる
> (CVE-2012-2459)。Bitcoin は「重複 txid の拒否」という後付けルールで
> 対処しているが、本仕様は構造的にこの問題を回避する。

さらにブロックヘッダは間接的にトランザクション数にコミットする
(コインベースの高さフィールドと合わせて検証される)。

## 6. 鍵とアドレス

### 6.1 アドレス形式

**bech32m (BIP350)** を用いる。SegWit v0 が bech32、v1 以降が bech32m という
Bitcoin の使い分けは歴史的経緯によるものであり、本チェーンは
**全バージョンで bech32m に統一する**。

```
<HRP> "1" <version> <payload(5bit変換)> <checksum(6文字)>
```

### 6.2 HRP (ネットワーク識別子)

| ネットワーク | HRP | 例 | 長さ |
| --- | --- | --- | ---: |
| mainnet | `oag` | `oag1q...` | 63 文字 |
| testnet | `toag` | `toag1q...` | 64 文字 |
| regtest | `roag` | `roag1q...` | 64 文字 |

HRP が一致しないアドレスはデコード時に拒否される MUST。
これによりネットワーク間の誤送金は構造的に発生しない。

### 6.3 アドレス版数

| version | 文字 | 内容 | 状態 |
| ---: | :---: | --- | --- |
| 0 | `q` | Schnorr x-only 公開鍵 (32 バイト) | v1 で実装 |
| 1 | `p` | 予約 (スクリプトハッシュ等) | 未定義 |
| 2–31 | | 予約 | 未定義 |

**前方互換性**: ウォレットは未知の version のアドレスに対して、
警告を表示した上で送金を許可する SHOULD。これにより将来 version を追加した際、
旧ウォレットからも新アドレスへ送金できる。

### 6.4 導出

```
秘密鍵 d  (32 バイト乱数, 1 ≤ d < n)
    │
    │  P = d × G
    ▼
公開鍵 P = (x, y)
    │
    │  BIP340: x のみを採用 (y は偶数を暗黙に選択)
    ▼
x-only 公開鍵 (32 バイト)
    │
    │  bech32m(HRP, version=0, payload)
    ▼
アドレス
```

ハッシュ関数は介在しない。公開鍵がそのままアドレスのペイロードとなる。

### 6.6 HD ウォレット

**BIP32 / BIP39 / BIP44** に準拠する。

```
m / 44' / <SLIP44> ' / <account> ' / <change> / <index>

change = 0  受取用
change = 1  お釣り用
ギャップリミット = 20
```

`SLIP44` のコインタイプ番号は **未登録** (→ [未決事項](#17-未決事項))。

secp256k1 を採用したことにより、BIP32 の**非強化導出**が利用できる。
これは拡張公開鍵 (xpub) のみから子アドレスを無限に生成できることを意味し、
サーバに秘密鍵を一切置かずに顧客ごとの入金アドレスを発行する運用が可能である。
(Ed25519 系ではこの運用は原理的に不可能である。)

### 6.7 アドレス再利用に関する注意

本チェーンは透明台帳である。同一アドレスを再利用すると、そのアドレスに紐づく
すべての取引履歴と残高が第三者から完全に閲覧可能となり、一度でも身元が
紐づけられれば過去・未来の全取引が特定される。

ウォレットは受取のたびに新しいアドレスを生成する MUST。

## 7. トランザクション

### 7.1 構造

```
Transaction {
    version:       u32
    input_count:   varint
    inputs:        TxInput[input_count]
    output_count:  varint
    outputs:       TxOutput[output_count]
    locktime:      varint          // u64 として解釈
}

TxInput {
    prev_txid:     [u8; 32]
    prev_index:    varint
    sig_len:       varint          // 64 または 65
    signature:     [u8; sig_len]
    sequence:      u32
}

TxOutput {
    amount:        varint          // u128 (atomic 単位)
    version:       u8              // アドレス版数
    payload_len:   varint          // 2〜40
    payload:       [u8; payload_len]
}
```

#### 出力が自己記述的であること

`payload_len` は省略できない。長さが版数から暗黙に決まる設計では、**未知の版数の
出力に遭遇したノードがそこで読み進められなくなる**。その結果、[§6.3](#63-アドレス版数)
と [§15.3](#153-将来の拡張余地) で確保した拡張枠を使うたびにハードフォークが
必要になってしまう。

長さを明示することで、版数 1 以降を追加してもすべての旧ノードが出力を読み飛ばせる
(意味を解さないため標準外として中継はしないが、ブロックの構造は読める)。
Bitcoin の出力が `scriptPubKey` に明示的な長さを持つのと同じ理由である。

コストは出力あたり 1 バイトである。

### 7.2 標準トランザクションのサイズ

本仕様における **基準トランザクション** を、1 入力 2 出力・金額が 9 バイトの
varint に収まる送金と定める。容量と手数料の見積もりはこれを単位とする。

```
入力  1 個:  prev_txid 32 + prev_index 1 + sig_len 1 + 署名 64 + sequence 4
                                                          = 102 バイト
出力  2 個:  (金額 9 + version 1 + payload_len 1 + payload 32) × 2
                                                          =  86 バイト
その他:      version 4 + 入力数 1 + 出力数 1 + locktime 1  =   7 バイト
──────────────────────────────────────────────────────
合計                                                      = 195 バイト
```

入力に公開鍵を含めない点に注意。使用対象の UTXO が既に公開鍵を保持している。

| 指標 | 値 |
| --- | ---: |
| 基準トランザクション | **195 バイト** |
| 200,000 バイトブロックあたりの件数 | 約 1,025 件 |
| スループット | 約 17.1 件/秒 |

#### 金額の符号化長は額に依存する

小数 16 桁を採用した結果、金額の varint 長は額によって変わる。

| 金額 | atomic 値 | varint 長 |
| ---: | ---: | ---: |
| 0.001 OAG | 10^13 | 7 バイト |
| 1 OAG | 10^16 | 8 バイト |
| **7.2058 OAG** | **2^56** | **8 → 9 バイトの境界** |
| 10 OAG | 10^17 | 9 バイト |
| 100 OAG | 10^18 | 9 バイト |
| 1,000 OAG | 10^19 | 10 バイト |

したがって同じ 1 入力 2 出力でも、少額送金 (7.21 OAG 未満) は **193 バイト**、
基準トランザクションは **195 バイト**、高額送金 (721 OAG 以上) は **197 バイト**
となる。見積もりには基準トランザクションを用いる。

これは小数桁数を 16 とした選択の直接の帰結である。8 桁であれば金額は
4〜5 バイトで済んだ。

### 7.3 手数料の表現

手数料は明示的なフィールドを持たない。

```
手数料 = Σ(入力が参照する UTXO の金額) − Σ(出力の金額)
```

この差額はコインベースを通じてマイナーが回収する。
**お釣りの出力を書き忘れると、差額の全額が手数料となる。**
ウォレットはこれを検出して警告する MUST。

### 7.4 locktime

```
locktime < 500,000,000   → ブロック高さとして解釈
locktime ≥ 500,000,000   → Unix 秒として解釈
locktime = 0             → 制約なし
```

時刻として解釈する場合、比較対象は直前ブロックの
**Median Time Past** (直近 11 ブロックのタイムスタンプの中央値) である。

条件は以下である。`locktime` は「このトランザクションを含められる最も早い
時点」を意味する。

```
高さとして解釈する場合:  ブロック高さ ≥ locktime
時刻として解釈する場合:  Median Time Past ≥ locktime
```

> **Bitcoin との差異**: Bitcoin は `locktime < 高さ` を条件とするため、
> `locktime = 100` のトランザクションが有効になるのは高さ 101 からである。
> この 1 つずれた意味論は混乱の元であり、本チェーンは採用しない。
> `locktime = 100` はちょうど高さ 100 から有効になる。

`locktime` は `u64` として保持する。`u32` では 2106 年に破綻するため。

### 7.5 sequence (相対 locktime)

BIP68 に準ずる意味論を定める。

```
bit 31 = 1  → 相対 locktime を無効化
bit 31 = 0  → 相対 locktime を有効化
    bit 22 = 0  → bits 0-15 をブロック数として解釈
    bit 22 = 1  → bits 0-15 を 512 秒単位として解釈
```

v1 において相対 locktime の**強制は行わない**が、フィールドの意味論は
本仕様で確定させる。将来ソフトフォークで強制を有効化できるようにするため。

### 7.6 コインベーストランザクション

ブロックの最初のトランザクションはコインベースである MUST。

```
CoinbaseTransaction {
    version:       u32
    input_count:   varint = 1
    input: {
        prev_txid:  [u8; 32] = すべて 0
        prev_index: varint   = 0xFFFFFFFF
        sig_len:    varint   // 追加ノンス用の任意データ長 (最大 100)
        signature:  [u8; sig_len]   // 先頭に height を varint で含む MUST
        sequence:   u32
    }
    output_count:  varint
    outputs:       TxOutput[]
    locktime:      varint = 0
}
```

`signature` フィールドは署名ではなく、マイナーの追加ノンス領域として使う。
先頭にブロック高さを含めることで、異なる高さのコインベースが
同一 txid を持つことを防ぐ (Bitcoin BIP34 と同趣旨)。

## 8. 署名対象 (Sighash)

**BIP341 方式**を採用する。

本チェーンはスクリプトを持たないため、BIP341 の `scriptPubKey` に相当するのは
出力の**支払い条件** (`version || payload_len || payload`。以下 lock と呼ぶ) である。

### 8.0 タグ付きハッシュ

```
tagged(tag, msg) = BLAKE3(tag のバイト列 || 0x00 || msg)
```

BIP340 は `SHA256(SHA256(tag) || SHA256(tag) || msg)` という構成を用いるが、
これは SHA-256 が長さ拡張攻撃を受けることへの対処である。BLAKE3 は構造的に
長さ拡張耐性を持つため、タグと NUL 区切りの前置で足りる。タグに NUL を
含めないため、この符号化は前置符号となり、異なるタグが同じ入力列を
生じることはない。

### 8.1 構成

```
msg =
    0x00                                       // エポック
    hash_type                          u8      // §8.3 のバイト
    tx.version                         u32 LE
    tx.locktime                        u64 LE

    ─── ANYONECANPAY でない場合のみ ───────────────────────
    tagged("OAG/sighash/prevouts",   全入力の prev_txid || prev_index)
    tagged("OAG/sighash/amounts",    全入力が参照する UTXO の金額)      ★
    tagged("OAG/sighash/locks",      全入力が参照する UTXO の lock)      ★
    tagged("OAG/sighash/sequences",  全入力の sequence)

    ─── 出力へのコミット (基本種別による) ─────────────────
    ALL / DEFAULT : tagged("OAG/sighash/outputs", 出力数 || 全出力)
    SINGLE        : tagged("OAG/sighash/outputs", 1 || 対応する出力)
    NONE          : (何も含めない)

    input_index                        u32 LE

    ─── ANYONECANPAY の場合のみ ───────────────────────────
    この入力の prev_txid || prev_index
    この入力が参照する UTXO の金額                                      ★
    この入力が参照する UTXO の lock                                     ★
    この入力の sequence                u32 LE

sighash = tagged("OAG/sighash", msg)
```

★ を付した 3 項目が [§8.2](#82-全入力金額へのコミット) の対象である。

`SINGLE` において対応する出力が存在しない場合、署名は生成できない。
Bitcoin の「ハッシュ値 1 を返す」という挙動は採用せず、明確な誤りとする。

### 8.2 全入力金額へのコミット

`H(すべての入力が参照する UTXO の金額)` を含めることが本仕様の重要点である。

> **背景**: Bitcoin の初期の sighash は入力金額にコミットしていなかった。
> このため、悪意ある PC がハードウェアウォレットに偽の入力金額を伝えて署名させ、
> 差額を全額マイナー手数料として流出させる攻撃が成立した。
> Bitcoin は BIP143 (SegWit) でこれを修正した。
> 本仕様は初版からこれを含め、ハードウェアウォレットが単独で手数料を
> 検算できるようにする。

### 8.3 Sighash フラグ

| 値 | 名称 | 意味 |
| ---: | --- | --- |
| `0x00` | DEFAULT | `ALL` と同義。署名は 64 バイト (フラグバイトを省略) |
| `0x01` | ALL | 全入力・全出力にコミット |
| `0x02` | NONE | 出力にコミットしない |
| `0x03` | SINGLE | 同じインデックスの出力のみにコミット |
| `0x81` | ALL \| ANYONECANPAY | 自分の入力のみ + 全出力 |
| `0x82` | NONE \| ANYONECANPAY | 自分の入力のみ |
| `0x83` | SINGLE \| ANYONECANPAY | 自分の入力 + 対応する出力のみ |

`0x00` 以外の場合、署名は 65 バイトとなり最終バイトがフラグとなる。

上表に無いバイト (`0x04` 以降、および `ANYONECANPAY` 単独の `0x80`) は
**未定義であり拒否する MUST**。

`SINGLE | ANYONECANPAY` は部分署名トランザクションの構築に用いる。
[相互運用性と DEX](#15-相互運用性と-dex) を参照。

## 9. ブロック

### 9.1 ブロックヘッダ (100 バイト固定)

```
BlockHeader {
    version:       u32        //  4  offset  0
    prev_hash:     [u8; 32]   // 32  offset  4
    merkle_root:   [u8; 32]   // 32  offset 36
    timestamp:     i64        //  8  offset 68   Unix 秒
    difficulty:    u64        //  8  offset 76
    height:        u64        //  8  offset 84
    nonce:         u64        //  8  offset 92
}                             // 合計 100 バイト
```

`nonce` を末尾に配置することで、マイナーは末尾 8 バイトのみを書き換えて
反復できる。

### 9.2 タイムスタンプが i64 である理由

Bitcoin のブロックヘッダは `u32` のタイムスタンプを持ち、
**2106 年 2 月 7 日にオーバーフローする**。

本チェーンの発行完了は 2026 年から約 190 年後、すなわち **2216 年**であり、
確実にこの時点を跨ぐ。したがって `u32` は採用できない。

### 9.3 難易度の表現

Bitcoin の `nBits` (4 バイト圧縮形式) は採用しない。難易度を `u64` で直接保持し、
ターゲットは以下で導出する。

```
MAX_TARGET = 2^256 − 1
target(difficulty) = MAX_TARGET / difficulty      (整数除算)
```

`nBits` は非正準な符号化や符号ビットの扱いに起因するバグを歴史的に生んでおり、
また LWMA は難易度を直接扱うため、`u64` の方が単純かつ安全である。

### 9.4 ブロック

```
Block {
    header:       BlockHeader
    tx_count:     varint
    transactions: Transaction[tx_count]
}
```

### 9.5 aux_pow (マージマイニング) の予約

`version` フィールドの **bit 0** を `AUX_POW` フラグとして予約する。

```
version & 0x00000001 == 0  → RandomX(header) を直接検証   (v1 の唯一の経路)
version & 0x00000001 == 1  → 親チェーンの PoW を検証       (未定義)
```

v1 においてこのビットが立ったブロックは**無効**とする。
将来 Monero とのマージマイニングを導入する際、
補助 PoW のデータはヘッダ外 (ブロック本体) に配置し、
ヘッダのサイズと構造は変更しない。

## 10. コンセンサスルール

### 10.1 パラメータ

```
TARGET_BLOCK_TIME        = 60 秒
MAX_BLOCK_SIZE           = 200,000 バイト
MAX_TX_SIZE              = 100,000 バイト
COINBASE_MATURITY        = 120 ブロック  (2 時間)
MEDIAN_TIME_SPAN         = 11 ブロック
MAX_FUTURE_TIME_DRIFT    = 300 秒
```

`MAX_FUTURE_TIME_DRIFT` は Bitcoin の 2 時間より大幅に短い。
60 秒ブロックにおいて 2 時間は 120 ブロック分の裁量を与えることになり、
難易度操作の余地が大きすぎるため。

### 10.2 ブロックの検証

ブロックは以下をすべて満たす MUST。

1. シリアライズサイズが `MAX_BLOCK_SIZE` 以下
2. `header.height == 親ブロックの height + 1`
3. `header.prev_hash` が既知の有効なブロックを指す
4. `header.timestamp > 親ブロックの Median Time Past`
5. `header.timestamp ≤ ノードの現在時刻 + MAX_FUTURE_TIME_DRIFT`
6. `header.difficulty` が [LWMA](#12-難易度調整-lwma) の計算結果と一致する
7. `header.version` の `AUX_POW` ビットが 0
8. PoW が有効 ([Proof of Work](#11-proof-of-work))
9. `header.merkle_root` がトランザクション列から再計算した値と一致する
10. 最初のトランザクションがコインベースであり、それ以外はコインベースでない
11. コインベースの `signature` 先頭の高さが `header.height` と一致する
12. すべてのトランザクションが有効
13. コインベース出力の合計 ≤ `block_subsidy(height) + 手数料合計`
14. 同一ブロック内で同一 UTXO を二重に使用していない
15. ブロックが空でない
16. コインベースに 1 個以上の出力があり、`MAX_TX_SIZE` を超えない

### 10.3 トランザクションの検証

1. 入力が 1 個以上、出力が 1 個以上ある
2. シリアライズサイズが `MAX_TX_SIZE` 以下
3. すべての入力が、UTXO セットに存在する未使用の出力を参照する
4. コインベース出力を参照する場合、`現在の高さ − 生成高さ ≥ COINBASE_MATURITY`
5. すべての出力金額が `0 ≤ amount ≤ MAX_SUPPLY`
6. `Σ入力 ≥ Σ出力` (checked 演算で評価。オーバーフロー時は無効)
7. すべての入力について、参照先の支払い条件を[§10.5](#105-未知の版数の扱い)に従って検査する
8. すべての入力の署名が [BIP340](#53-署名-schnorr-bip340) 検証を通過する
9. `locktime` の条件を満たしている
10. 同一トランザクション内で同一 UTXO を二重に使用していない

### 10.5 未知の版数の扱い

出力の版数がノードにとって未知である場合、**コンセンサス上は誰でも使用できる
(anyone-can-spend) ものとして扱い、署名を検査しない MUST**。

#### なぜ拒否してはならないか

未知の版数を無効としてしまうと、新しい版数を導入するたびに旧ノードが
新しいブロックを拒否することになり、**版数の追加が必ずハードフォークになる**。
それでは出力に長さ接頭辞を設けた意味 ([§7.1](#71-構造)) が失われる。

anyone-can-spend としておけば、後から**ソフトフォークで条件を厳しくする**ことで
版数を有効化できる。旧ノードから見れば「誰でも使えるはずの出力を、新ノードが
より厳しく検査している」だけであり、新ノードが作るブロックは旧ノードにとっても
有効なままである。Bitcoin が SegWit の導入に用いたのと同じ機構である。

#### 伴う危険

**版数が有効化されるまでの間、その版数のアドレスへ送金してはならない。**
誰でも取り出せる資金になる。以下で緩和する。

| 層 | 対策 |
| --- | --- |
| ウォレット | 未知の版数のアドレスへの送金時に警告する ([§6.3](#63-アドレス版数)) |
| ノードポリシー | 未知の版数を含む出力を作るトランザクションを中継しない |
| ノードポリシー | 未知の版数の出力を使用するトランザクションを中継しない |

ポリシー層の 2 つはコンセンサスルールではないため、マイナーが直接ブロックに
含めることは妨げられない。これは Bitcoin と同じ性質である。

### 10.4 検証順序 (DoS 対策)

RandomX の light モード検証は 1 ハッシュあたり数ミリ秒を要する。
攻撃者が無効なヘッダを大量送信することでノードの CPU を枯渇させられるため、
**PoW の検証は最後に行う MUST**。

```
① 親ブロックが既知か                (ハッシュマップ参照)
② height が親 + 1 か               (整数比較)
③ timestamp が範囲内か             (整数比較)
④ difficulty が期待値と一致するか    (整数比較)
⑤ version の AUX_POW ビットが 0 か  (ビット演算)
   ────── ここまで通過したもののみ ──────
⑥ RandomX 検証                    (数ミリ秒)
```

加えて、ピアごとにヘッダ受信のレート制限を適用する MUST。

### 10.5 最長チェーンの選択

累積作業量 (各ブロックの `difficulty` の総和) が最大のチェーンを採用する。
ブロック数ではなく作業量で比較する。

再編成 (リオーグ) の深さに上限は設けない (→ [未決事項](#17-未決事項))。

## 11. Proof of Work

### 11.1 アルゴリズム

**RandomX** ([tevador/RandomX](https://github.com/tevador/RandomX), MIT) を用いる。
Rust からは C++ 参照実装への FFI で利用する。

```
pow_hash = RandomX(seed_hash, header_serialized)
有効条件: pow_hash (ビッグエンディアン u256 として解釈) ≤ target(difficulty)
```

### 11.2 動作モード

| モード | メモリ | 用途 |
| --- | ---: | --- |
| fast | 2 GB / スレッド | マイニング |
| light | 256 MB | ノードの検証 |

フルノードは light モードで動作可能である MUST。
すなわち、ノード運用に 2 GB のデータセットは要求しない。

**スレッド安全性**: RandomX の VM は内部にスクラッチパッドを持つため、
複数スレッドで共有してはならない。並列に検証または採掘する場合は、
**スレッドごとに VM を持つ MUST**。light モードでもスレッドあたり
256 MB のキャッシュを要する点に注意する
(キャッシュ自体は共有可能だが、本実装は単純さを優先して共有していない)。

### 11.3 シードエポック

RandomX のシードは一定間隔で切り替わる。Monero と同じ方式を採用する。

```
SEED_EPOCH_BLOCKS = 2048        (約 34 時間)
SEED_LAG          = 64 ブロック

seed_height(h) = ((h − SEED_LAG) / 2048) × 2048      (h ≥ 2048 + SEED_LAG の場合)
seed_hash      = seed_height のブロックハッシュ
```

エポックをこれより短くすると、マイナーが 2 GB のデータセットを再構築する
頻度が上がる (1 回あたり 1〜2 分) ため、実効ハッシュレートが低下する。

`SEED_LAG` は、リオーグによってシードが変化することを防ぐための猶予である。

## 12. 難易度調整 (LWMA)

### 12.1 アルゴリズム

**LWMA-1** ([zawy12/difficulty-algorithms](https://github.com/zawy12/difficulty-algorithms))
を採用する。毎ブロック調整する。

```
T = 60                        目標ブロック時間 (秒)
N = 90                        窓幅 (暫定値)
k = N × (N + 1) × T / 2

L = 0
sum_D = 0
for i in 1..=N:
    st = clamp(timestamp[i] − timestamp[i−1], −6×T, +6×T)
    L += st × i
    sum_D += difficulty[i]

if L < k / 10:
    L = k / 10                // 難易度の急騰を抑える下限

next_difficulty = (sum_D × k) / (N × L)
```

タイムスタンプの逆転 (負の solvetime) を許容し、クランプで扱う点が
LWMA の特徴である。

### 12.2 窓幅 N の検証

`N = 90` (90 分の窓) を採用する。以下は実装したシミュレーション
(`crates/oag-pow/src/lwma.rs` のテスト) による実測値である。
solvetime は指数分布に従わせ、乱数は決定的なため結果は再現する。

#### 定常状態

| 乱数種 | 平均ブロック間隔 | 難易度の最大振れ幅 |
| ---: | ---: | ---: |
| 1 | 60.55 秒 | 均衡値の 1.62 倍 |
| 2 | 60.51 秒 | 1.33 倍 |
| 3 | 60.50 秒 | 1.53 倍 |

目標 60 秒に対して 1 % 以内に収まっている。

#### ハッシュレート変動への追随

均衡難易度の誤差 20 % 以内に入るまでの所要。

| 変化 | ブロック数 | 実時間 |
| --- | ---: | ---: |
| 2 倍 | 31 | 0.20 時間 |
| **10 倍** | **99** | **0.70 時間** |
| 1/2 | 74 | 1.70 時間 |
| **1/10** | **145** | **5.64 時間** |

#### 非対称性という既知の弱点

上表のとおり、**ハッシュレートの増加には速く追随するが、減少からの回復は
遅い**。10 倍への追随が 0.7 時間なのに対し、1/10 への回復には 5.6 時間かかる。

これは PoW チェーン共通の性質である。ハッシュレートが失われるとブロック間隔が
伸びるため、難易度を下げるのに必要なブロック数を消化する実時間が長くなる。
窓幅を縮めれば回復は速くなるが、定常状態の振れ幅が大きくなる。

現実的な影響は、**大きなハッシュレートが一時的に流入して離脱すると、
その後数時間チェーンが遅くなる**ことである。小規模チェーンにとっては
実害のある性質であり、[§15](#15-相互運用性と-dex) で触れた
Monero とのマージマイニングは、この変動そのものを小さくする対策でもある。

本仕様は N = 90 を採用したうえで、この弱点を既知のものとして受け入れる。

### 12.3 立ち上げ期

```
height < N + 1  →  difficulty = GENESIS_DIFFICULTY (固定)
height ≥ N + 1  →  LWMA を適用
```

## 13. 手数料ポリシー

### 13.1 二層構造

手数料は**コンセンサスルールではなくノードポリシー**として扱う。

```
コンセンサス層 (全ノードが強制、変更にハードフォークが必要)
  └ 手数料の下限を設けない。Σ入力 ≥ Σ出力 のみを要求する

ノードポリシー層 (各ノードの設定、いつでも変更可能)
  └ MIN_RELAY_FEE_RATE 未満のトランザクションは中継せず mempool にも保持しない
```

この分離により、OAG の価格変動に対して**ハードフォークなしで**
最低手数料を調整できる。

### 13.2 既定値

```
MIN_RELAY_FEE_RATE = 0.000005 OAG / バイト
                   = 50,000,000,000 atomic / バイト   (5 × 10^10)

基準トランザクション (195 バイト) の手数料 = 0.000975 OAG
```

### 13.3 ダスト閾値

未使用の UTXO はすべてのノードが恒久的に保持するため、
極小額の出力を大量生成する攻撃は全ノードのメモリを永続的に汚染する。

```
1 入力を消費するコスト = 102 バイト × 0.000005 = 0.00051 OAG
その 3 倍              = 0.00153 OAG
DUST_THRESHOLD        = 0.0015 OAG   (政策値として丸めた。倍率は約 2.94)
                      = 15,000,000,000,000 atomic  (1.5 × 10^13)
```

`DUST_THRESHOLD` 未満の出力を含むトランザクションは中継しない
(ノードポリシー。コンセンサスルールではない)。

### 13.3.1 未知の版数の扱い (ポリシー層)

[§10.5](#105-未知の版数の扱い) のとおり、未知の版数の出力はコンセンサス上
誰でも使用できる。ポリシー層では以下を既定とする。

- 未知の版数の出力を**作る**トランザクションを中継しない
- 未知の版数の出力を**使う**トランザクションを中継しない

前者は、有効化前のアドレスへ送金して資金を失う事故を防ぐためである。
後者は、そのような資金の横取りを助けないためである。

いずれもポリシーであり、マイナーが直接ブロックに入れることは妨げられない。

### 13.3.2 手数料を上げた置き換え (RBF) は未対応

同じ UTXO を使う別のトランザクションが後から来た場合、手数料が高くても
**受け付けない**。先に来たものを保持する。

RBF は手数料市場の効率を上げるが、ゼロ承認取引の扱いを変えるため、
導入するなら方針として明示的に決める必要がある
([未決事項](#17-未決事項)を参照)。

### 13.4 スパム耐性の評価

```
200,000 バイトのブロックを埋め尽くすコスト
  = 200,000 × 0.000005 = 1.0 OAG / ブロック
  = 1,440 OAG / 日
```

立ち上げ期において、これは十分に安価である。
これは PoW チェーン共通の性質であり、本仕様で解決するものではない。

### 13.5 チェーン成長の見積もり

```
200,000 バイト × 525,600 ブロック/年 = 約 105 GB/年 (満杯時)
```

したがって以下を v1 から実装する MUST。

- **プルーニング**: 検証済みの古いブロック本体を破棄し、
  UTXO セットとヘッダのみを保持するモード
- **UTXO スナップショット同期**: 新規ノードが全履歴を検証せずに
  参加できる経路 (Bitcoin の assumeutxo 相当)

### 14.1 ポート

| ネットワーク | P2P | RPC | Mining |
| --- | ---: | ---: | ---: |
| mainnet | 9444 | 9445 | 9446 |
| testnet | 19444 | 19445 | 19446 |
| regtest | 29444 | 29445 | 29446 |

命名規則: `testnet = mainnet + 10000`、`regtest = mainnet + 20000`。

#### 既存チェーンとの衝突回避

以下のポートは既存の主要チェーンが事実上占有しているため採用しない。

| ポート | 用途 |
| ---: | --- |
| 8332 / 8333 | Bitcoin RPC / P2P |
| 8444 | Chia |
| 8232 / 8233 | Zcash |
| 9332 / 9333 | Litecoin |
| 9999 | Dash |
| 18080 / 18081 | Monero P2P / RPC |
| 18333 | Bitcoin testnet |
| **18444** | **Bitcoin regtest** |
| 22556 | Dogecoin |
| 30303 | Ethereum devp2p |

特に **Bitcoin の 8333 を採用してはならない**。プロトコルの混線はマジックバイトに
よって防がれるため安全性の問題ではないが、以下の運用上の不利益を無償で相続する。

1. 同一ホストで Bitcoin ノードと同居できない
2. Bitcoin のピアゴシップとクローラから恒常的に接続試行を受ける
3. 8333 を Bitcoin の特徴として遮断する企業ファイアウォール・ISP・検閲装置の
   影響を受ける
4. 一部のホスティング事業者のポリシーに抵触する

Bitcoin の regtest が 18444 を用いるため、本チェーンの testnet は 18444 ではなく
**19444** とする。

#### バインドアドレスの既定値

| サービス | 既定のバインド先 | 理由 |
| --- | --- | --- |
| P2P | `0.0.0.0` | 外部からの接続受け入れが前提 |
| **RPC** | **`127.0.0.1` のみ** | 資金操作が可能なため |
| **Mining** | **`127.0.0.1` のみ** | 同上 |

RPC を外部に公開した結果として資金を喪失する事故は、Bitcoin・Ethereum・Monero を
含む複数のプロジェクトで実際に発生している。既定値でこれを防ぐ MUST。

マイニング用インタフェースを RPC と分離する理由は、マイナーの接続を許可するために
RPC を外部公開せざるを得ない状況を構造的に避けるためである。

### 14.2 マジックバイト

すべてのメッセージの先頭に置く 4 バイトである。ハンドシェイクの最初に
検証され、**ネットワーク間の分離を担う実質的な機構である**。ポート番号は
運用上の慣習にすぎず、分離を保証しない。

値は恣意的に選ぶのではなく、ネットワーク名から決定的に導出する。

```
magic = BLAKE3("Orange/network/<ネットワーク名>")[0..4]
```

| ネットワーク | 導出元 | 値 |
| --- | --- | --- |
| mainnet | `Orange/network/mainnet` | `33 97 55 03` |
| testnet | `Orange/network/testnet` | `7F 88 A0 C1` |
| regtest | `Orange/network/regtest` | `18 2C 9C 5E` |

いずれも印字可能な ASCII のみからは成らない。平文の流れの中に偶然
現れにくくするためである。

### 14.3 ジェネシス難易度 (暫定)

| ネットワーク | 難易度 |
| --- | ---: |
| mainnet | 100,000 |
| testnet | 1,000 |
| regtest | 1 |

RandomX の単一 CPU コアの性能をおよそ 1,000 H/s と仮定した値である。
実測に基づいて調整する。

### 14.4 P2P プロトコル

**独自実装**とする。rust-libp2p は採用しない。

PoW チェーンの P2P 要件は「ブロックとトランザクションの伝播」に尽き、
libp2p の DHT や多様なトランスポートはオーバースペックであり、
依存の重さと仕様変更の追随コストが利益を上回ると判断した。

実装する機能:

- ハンドシェイク (`version` / `verack`)
- ピア探索 (シードノード + アドレス交換)
- `inv` / `getdata` によるトランザクション伝播
- **headers-first 同期**

- **Compact Blocks** — [§14.7](#147-compact-blocks) を参照。v1 から必須とする

### 14.5 メッセージの枠組み

```
magic     [4]   ネットワーク識別子
command  [12]   コマンド名。ASCII 小文字、余りは NUL 埋め
length    [4]   ペイロード長 (u32 LE)
checksum  [4]   BLAKE3(payload)[0..4]
payload  [長さ]
```

前置きは 24 バイトである。

#### 長さの検査は読み込む前に行う MUST

宣言されたペイロード長が上限を超えていたら、**ペイロードを 1 バイトも
読まずに接続を切る**。長さだけを大きく偽って接続を保つことで、相手の
メモリを枯渇させる攻撃を防ぐため。

```
ペイロード長の上限   1 MiB
```

最大のブロック (200,000 バイト) と、上限まで詰めた `inv`
(5,000 項目 × 33 バイト = 165,000 バイト) の双方が余裕をもって収まる。

#### 項目数の上限

| メッセージ | 上限 |
| --- | ---: |
| `inv` / `getdata` / `notfound` | 5,000 項目 |
| `headers` | 2,000 件 |
| `addr` | 1,000 件 |
| `getheaders` のロケータ | 64 件 |
| ユーザエージェント | 64 バイト |

### 14.6 ハンドシェイク

```
自分 ──version──▶ 相手
自分 ◀──version── 相手
自分 ──verack───▶ 相手
自分 ◀──verack─── 相手
```

両方向がそろって初めて通常のやり取りに入る。**完了前に本題のメッセージを
受け取ったら接続を切る MUST**。名乗っていない相手にブロックを配らないため。

`version` に含める乱数は自己接続の検出に用いる。相手の `version` に自分と
同じ乱数が入っていたら、それは自分自身への接続である。

### 14.7 Compact Blocks

ブロックを丸ごと送らず、**相手がすでに持っているものは送らない**。

```
cmpctblock
  header      100 バイト
  nonce         8 バイト
  短縮 ID       6 バイト × (取引数 − 埋め込んだ数)
  埋め込み取引  コインベースは相手が持たないので必ず含める
```

受け取った側は mempool から短縮 ID の一致するものを拾い、足りない分だけ
`getblocktxn` で番号を指定して求める。

#### 実測

`crates/oag-net/src/compact.rs` の試験による実測値である。

| ブロック内の取引数 | `block` | `cmpctblock` | 比 |
| ---: | ---: | ---: | ---: |
| 10 | 1,710 B | 270 B | 6 |
| 100 | 15,300 B | 810 B | 19 |
| 500 | 75,701 B | 3,211 B | 24 |
| **1,000** | **151,201 B** | **6,211 B** | **24** |

10 Mbps の回線で 1,000 件のブロックを送り出す時間は **121 ms から 5 ms**
になる。

#### なぜ 60 秒ブロックで重要か

伝播に時間がかかるほど、同じ高さのブロックが並行して掘られる確率
(孤児率) が上がる。孤児率が高いと、接続の良い大規模なマイナーが有利になり
中央集権化が進む。[§7.2](#72-標準トランザクションのサイズ) で見たとおり、
本チェーンは 200,000 バイトを 60 秒間隔で撒くため、これがないと孤児率が
2〜3 % に達する。

#### 短縮 ID の衝突

短縮 ID は 6 バイトしかないため、mempool の中の無関係な取引と偶然一致
しうる。その場合、組み立てたブロックは**間違ったものになる**。

**組み立ての最後に必ずマークルルートを検証する MUST。** 合わなければ捨てて
通常の `block` を求め直す。これにより、衝突も、相手が誤った取引を返した
場合も捕まる。

短縮 ID の鍵はブロックごとに変わる。

```
key      = BLAKE3("OAG/cmpct/shortid" || header || nonce)
short_id = BLAKE3_keyed(key, txid)[0..6]
```

鍵が固定であれば、攻撃者が衝突する取引をあらかじめ用意して全ノードを
一斉に妨害できてしまう。ブロックごとに変えることでこれを防ぐ。

### 14.8 ストレージ

**redb** (純 Rust の埋め込み ACID データベース) を用いる。

rocksdb は実績で勝るが C++ 依存でクロスコンパイルが煩雑になる。
UTXO セットの規模において redb の性能は十分と判断した。

## 15. 相互運用性と DEX

### 15.1 前提

本チェーンは以下の 2 つの性質を持つ。

1. **資産が OAG の 1 種類のみである。** トークン発行機能を持たない。
2. **スクリプト言語を持たない。** 条件付き支払いを直接表現できない。

したがって:

| 種類 | 可否 |
| --- | :---: |
| クロスチェーン アトミックスワップ (OAG ↔ BTC / LTC / XMR 等) | **可能** |
| P2P スワップ市場 (板はオフチェーン、決済はスワップ) | **可能** |
| 他チェーンへブリッジして既存 DEX で取引 | **可能** (要ブリッジ運営) |
| 同一チェーン内の板取引 DEX | **不可** (交換相手の資産が存在しない) |
| AMM 型 DEX (Uniswap 等) | **不可** (実行環境がない) |
| レンディング / デリバティブ | **不可** (同上) |

### 15.2 アダプター署名によるアトミックスワップ

Schnorr 署名の線形性により、**スクリプトを一切用いずに**
クロスチェーンのアトミックスワップが構成できる。

```
1. 両者が MuSig2 で 2-of-2 の集約鍵を作り、そこへ資金を送る
   → チェーン上は通常の単一署名の送金と区別がつかない

2. 資金を送る前に、locktime 付きの返金トランザクションを相互に事前署名する
   → 相手が離脱しても時間経過後に取り戻せる

3. 一方のチェーンで署名が公開されると、アダプター署名の性質により
   その署名から秘密値が復元でき、他方のチェーンの資金が解錠される
```

**HTLC 方式に対する優位性**:

- スクリプトを必要としない (本チェーンで実現可能な唯一の方式)
- 両チェーンに同一のハッシュ値が刻まれないため、
  2 つの取引が関連していることが外部から判別できない
- 通常の送金と同じサイズ・同じ形式

**成立に必要なプロトコル要件** (すべて本仕様に含まれている):

| 要件 | 該当箇所 |
| --- | --- |
| BIP340 Schnorr 署名 | [5.3](#53-署名-schnorr-bip340) |
| トランザクション ID の非展性 | [5.3](#53-署名-schnorr-bip340) |
| 絶対 locktime | [7.4](#74-locktime) |
| 相対 locktime の意味論 | [7.5](#75-sequence-相対-locktime) |
| Sighash フラグ | [8.3](#83-sighash-フラグ) |

MuSig2 とアダプター署名は**完全にウォレット層の技術**であり、
コンセンサスの変更を一切必要としない。したがって v1 では実装せず、
後からウォレット側の機能追加として提供できる。

### 15.3 将来の拡張余地

より高度な取引機能が必要になった場合の拡張経路を、
アドレス版数の予約領域として確保してある ([6.3](#63-アドレス版数))。

```
version 1 →  ハッシュロック + タイムロック (HTLC 型出力)
version 2 →  スクリプトハッシュ
```

これらはソフトフォークとして追加できる (旧ノードは未知の version の出力を
「誰でも使用可能」とみなすのではなく、標準外として中継しないため)。

**AMM を実現するには任意計算の実行環境が必要であり、
それは本仕様の範囲を超える別の設計となる。**

## 16. 設計判断の記録

主要な選択と、その理由を記録する。

| 判断 | 選択 | 理由 |
| --- | --- | --- |
| 合意形成 | PoW (RandomX) | CPU 採掘による公平な分配。ASIC 耐性 |
| 実装言語 | Rust | GC がなくブロック検証のレイテンシが決定的。型システムがコンセンサス状態機械に適する。RandomX の FFI が cgo より軽い。Tari という先例 |
| 会計モデル | UTXO | 検証が単純。並列検証が容易 |
| 署名曲線 | secp256k1 | libsecp256k1 の実績。ハードウェアウォレット対応。BIP32 の非強化導出が使える |
| 署名方式 | Schnorr (BIP340) | 展性がない。64 バイト固定。バッチ検証。MuSig2 とアダプター署名が使える |
| 汎用ハッシュ | BLAKE3 | 高速。Rust が参照実装。長さ拡張耐性があり二重ハッシュ不要 |
| 金額型 | u128 | 10^25 atomic は u64 に収まらない |
| 小数桁数 | 16 | — |
| 発行カーブ | 線形・半減期なし | 実装が単純でオフバイワンの余地がない。半減期に伴うハッシュレートの断崖がない。長期にわたり新規参加者に採掘機会が残る |
| 初期配布 | なし | 公平な分配という設計目標の中核 |
| タイムスタンプ | i64 | 発行完了が 2216 年であり u32 は 2106 年に破綻する |
| 難易度表現 | u64 直接 | nBits の非正準符号化に起因するバグ類を回避。LWMA が難易度を直接扱う |
| マークルツリー | RFC 6962 | Bitcoin の CVE-2012-2459 を構造的に回避 |
| アドレス | bech32m | 4 文字以内の誤りを 100 % 検出。大文字小文字の混在を禁止。QR が小さい |
| 手数料 | バイト単価 / ノードポリシー | スクリプトがないためガス (計算量課金) は不要。価格変動にハードフォークなしで追随できる |
| プライバシー | なし | 実装量と監査費を大幅に削減。取引サイズが Monero の約 1/8 |
| P2P | 独自実装 | 要件が単純。libp2p の依存の重さが利益を上回る |
| ストレージ | redb | 純 Rust でクロスコンパイルが容易 |
| マージマイニング | v1 では無効 | 単体チェーンのデバッグと Monero 連携のデバッグを同時に走らせない。ヘッダに拡張枠のみ確保 |

### 検討したが採用しなかったもの

| 案 | 不採用の理由 |
| --- | --- |
| Cosmos SDK / 独自 PoS チェーン | RandomX (PoW) と両立しない |
| ERC-20 トークンとして発行 | 独自チェーンを持つという目標に反する |
| Go 言語 | RandomX が cgo 経由となり、呼び出しコストとクロスコンパイルの負担が Go の開発速度の利点を相殺する |
| ECDSA | 展性がある。バッチ検証ができない。MuSig2 が使えない |
| Ed25519 | BIP32 の非強化導出が使えず xpub 運用ができない。ハードウェアウォレット対応が重い |
| 半減期方式 | 総発行 10 億・報酬 10 OAG と両立させるには半減期が 95 年となり機能しない |
| プライバシー機能 (RingCT 等) | 実装量と監査費が過大。取引サイズが 8〜12 倍になる |
| 1 MB ブロック | 年間 526 GB の成長となりノード運用が不可能になる |
| SegWit 相当の機構 | Schnorr + スクリプトなしの構成では展性が存在せず不要 |

## 17. 未決事項

実装フェーズで決定する項目。

### 優先度: 高

- [ ] **SLIP-0044 コインタイプ番号** — 未登録。`satoshilabs/slips` への PR が必要。
      登録前に暫定値で運用すると、後の変更で既存ウォレットの資金が
      見えなくなるため早期に着手する
- [ ] **ジェネシスブロック** — 以下を決めたうえで実際に採掘し、ハッシュを確定する。
      一度確定させたら変更できない (変えれば別のチェーンになる)。
      - タイムスタンプ
      - コインベースに刻むメッセージ。恒久的に公開され、「この時点より前に
        採掘されていないこと」の証拠にもなる (Bitcoin が新聞の見出しを
        刻んだのと同じ位置づけ)
      - **ブロック 0 の報酬を受け取るか放棄するか。** 放棄すれば 10 OAG が
        永久に発行されず、プレマインが無いことが最も明確になる。受け取る場合も
        他のブロックと同じ 1 ブロック分にすぎず、総発行量の 0.000001 % である
- [ ] **ジェネシス難易度** — RandomX の実測に基づく調整

### 優先度: 高

- [ ] **未知の版数を anyone-can-spend とする判断の確認**
      ([§10.5](#105-未知の版数の扱い))。ソフトフォークによる版数追加を
      可能にする代わりに、有効化前のアドレスへ送金すると資金を失う。
      Bitcoin と同じ選択だが、資金喪失に直結するため方針の再確認を要する

### 優先度: 中

- [ ] **トランザクション索引を設けるか** — 現在、txid から取引を引く索引は
      持たない。コンセンサスが必要とする索引は UTXO セットだけであり、
      検証が「この txid の取引はどこか」を問う場面は無いためである
      (入力が指すのは常に `OutPoint` である)。
      満杯のブロックが続く場合、全取引の索引は年間 35 GB を要する
      (チェーン本体 105 GB/年に対して 3 分の 1 の上乗せ)。
      Bitcoin が `-txindex` を既定で無効にしているのと同じ理由である。
      ウォレットは自分に関係する取引だけを記録すれば足りる。
      任意機能として設けるかは、エクスプローラや RPC の要求次第で決める

- [ ] **コインベース成熟の再検討** — 120 ブロック (2 時間) は
      低ハッシュレート期の深いリオーグに対して十分か
- [ ] **最大リオーグ深度** — 制限を設けるか。設けると 51 % 攻撃への防御になるが、
      恒久的なチェーン分裂を招く危険がある
- [ ] **手数料を上げた置き換え (RBF) を導入するか** — 現在は未対応で、
      同じ UTXO を使う後発のトランザクションは手数料が高くても受け付けない。
      導入すると手数料市場の効率は上がるが、ゼロ承認取引の前提が変わる
- [ ] **部分署名トランザクション形式** — PSBT 相当。ウォレット間の相互運用に必要。
      署名には各入力が参照する UTXO の金額と lock が必要なため
      ([§8.2](#82-全入力金額へのコミット))、この形式はそれらを運ぶ必要がある

- [ ] **シードノードのホスト名**
