# 作ったもの

**Orange** (記号 `OAG`)。RandomX を Proof of Work に使う、CPU マイニング型の UTXO ブロックチェーンです。Rust で一から書きました。

# なぜ作ったのか

## 「fork でいいのでは？」への答え

草コインを作る方法は、ふつう 2 つあります。

1. **既存チェーンの上にトークンを出す** (ERC-20 / SPL など)。合意形成の実装が要らない。数分でできる
2. **既存チェーンを fork する**。Bitcoin や Litecoin のコードを持ってきて、名前・ジェネシス・定数を書き換える

どちらも選びませんでした。理由は、**やりたかったことが定数では表現できなかった**からです。

設計目標は 3 つあります。

1. **公平な分配** — プレマイン・ICO・開発者報酬を一切持たない
2. **単純さ** — スクリプト言語も仮想マシンも持たない。検証するのは署名と金額の帳尻だけ
3. **長期的な分配** — 半減期を持たない線形発行

2 番目が効きました。**Bitcoin を fork して「スクリプトを消す」のは、定数の書き換えではなく心臓の入れ替え**です。sighash の定義が変わり、アドレスの意味が変わり、手数料の考え方が変わる。fork した土台の上でそれをやるくらいなら、最初から書いたほうが読める状態になります。

3 番目も同じです。後述しますが、半減期の有無は 1 行の定数ではなく、発行カーブの形そのものです。

## 「単純さ」は思想ではなく予算の話

スクリプトを持たないという決定は、格好つけではありません。**監査できる量に収める**ための決定です。

個人で書いて個人で読むコードに、VM と opcode とガス計算を載せたら、検証しきれないまま mainnet が動くことになります。実際に落とした機能を並べると、こうなります。

| 落としたもの | 理由 |
| --- | --- |
| スクリプト言語・VM | 攻撃面が跳ね上がる。手数料にガス(計算量課金)が必要になる |
| プライバシー (RingCT 等) | 実装量と監査費が過大。取引サイズが 8〜12 倍 |
| SegWit 相当の機構 | Schnorr + スクリプトなしでは展性が存在せず、不要 |
| マージマイニング (v1) | 単体チェーンのデバッグと連携のデバッグを同時に走らせない |

落とした分、**トランザクションの検証は「署名が正しいか」と「入力の合計 ≧ 出力の合計」だけ**になりました。これは読み切れます。

# Bitcoin が踏んだ地雷を、ブロック 1 の前に塞ぐ

一から書く最大の利点はこれです。**Bitcoin が 17 年かけて見つけたバグが、全部公開されている**。fork するとその地雷も一緒に持ってくることがありますが、一から書けば最初から避けられます。

実際に塞いだものを挙げます。

## 1. 金額の桁溢れ (CVE-2010-5139)

2010 年 8 月、Bitcoin は **1,844 億 BTC を生成する事故**を起こしました。出力金額の合計が `int64` を溢れて、検査をすり抜けたためです。

対策は単純で、**合算は必ず `checked_add`**。`u128` を使い、溢れたら `None` が返って検証が落ちます。

```rust
// 合算は Option を返す。溢れたら None。
pub fn total_output(&self) -> Option<Amount> {
    Amount::sum(self.outputs.iter().map(|o| o.amount))
}
```

呼ぶ側は、溢れをそのまま検証エラーに落とします。

```rust
let coinbase_value = coinbase
    .total_output()
    .ok_or(ValidationError::AmountOverflow)?;
let allowed = params::block_subsidy(header.height)
    .checked_add(total_fees)
    .ok_or(ValidationError::AmountOverflow)?;
```

金額型を `u128` にしたのは格好つけではなく、**10^25 atomic が `u64` に収まらない**からです (総発行 10 億 OAG × 10^16)。

## 2. マークルツリーの重複ノード (CVE-2012-2459)

Bitcoin のマークルツリーは**奇数個のノードを複製して埋める**設計です。このため、**異なる取引集合が同じマークル根を持てて**しまいました。Bitcoin は「重複 txid の拒否」という後付けルール (BIP30) で塞いでいます。

Orange は **RFC 6962** (Certificate Transparency) のマークルツリーを使います。**葉と内部ノードで別のドメイン分離タグを付ける**ため、この曖昧さが構造的に存在しません。後付けルールが要らない。

## 3. sighash が入力金額にコミットしていなかった

Bitcoin の初期の sighash は、**署名する取引の入力金額を含んでいませんでした**。これはハードウェアウォレットに対する攻撃になります (署名する機械が、自分が何円払うのか分からない)。Bitcoin は BIP143 で後から直しました。

Orange の sighash は最初から**全入力の金額と支払い条件にコミット**します。BIP341 (Taproot) の設計を踏襲しています。

## 4. タイムスタンプの `u32`

Bitcoin のブロックヘッダは `u32` のタイムスタンプを持ち、**2106 年に破綻**します。Orange の発行完了は 2216 年なので、`u32` では足りません。`i64` にしてあります。

## 5. `nBits` の非正準符号化

Bitcoin は難易度を 4 バイトの圧縮形式 (`nBits`) で持ちますが、**同じ値に複数の符号化がある**ためバグの温床になっています。Orange は難易度を `u64` で直接持ちます。使う LWMA が難易度を直接扱うので、圧縮する動機もありません。

## 6. 未来のタイムスタンプ許容幅

Bitcoin は自ノードの時刻より **2 時間先**までのタイムスタンプを許します。これは 10 分ブロックの話です。60 秒ブロックで 2 時間を許すと、**120 ブロック分の裁量**を採掘者に与えることになり、難易度操作の余地が大きすぎます。

Orange は **300 秒**にしました。

# 半減期を作らなかった理由

「Bitcoin に半減期があるから半減期を入れる」は、カーゴカルトになりがちです。実際に数を入れてみると、**この設計では半減期が成立しない**ことが分かります。

半減期方式の総発行量は等比級数の和なので、

```
総発行量 = 報酬 × 半減期の間隔 × 2
```

総発行 10 億 OAG、報酬 10 OAG を入れると、

```
1,000,000,000 = 10 × N × 2
N = 50,000,000 ブロック

50,000,000 ÷ 525,600 ブロック/年 ≒ 95.1 年
```

**半減期が 95 年**になります。人間の一生より長い周期は、半減期として機能しません。

そこで線形発行にしました。利点は 3 つあります。

1. **実装が単純**。`if height < EMISSION_END_HEIGHT { BLOCK_REWARD } else { ZERO }` の 1 行で、オフバイワンの余地がない
2. **ハッシュレートの断崖がない**。半減期のたびに採掘者の収入が半分になる衝撃が発生しない
3. **新規参加者に採掘機会が長く残る**

3 番目は数字で見ると分かりやすいです。

| | Bitcoin | Orange |
| --- | --- | --- |
| 最初の 4 年で出る量 | **総量の 50 %** | **総量の 2.1 %** |

Bitcoin は最初の 4 年 (210,000 ブロック × 50 BTC) で総量の半分が出ます。設計として**早く来た者ほど多く取る**構造です。Orange は同じ 4 年で 2.1 % しか出ません。

代償として、**190 年後に報酬が 10 OAG から 0 になる断崖**が 1 ブロックの境目で発生します。そこは正直に仕様書の「未決事項」に書いてあります。

```rust
/// 半減期は存在しない。発行終了高さまで一定である。
pub const fn block_subsidy(height: u64) -> Amount {
    if height < EMISSION_END_HEIGHT {
        BLOCK_REWARD
    } else {
        Amount::ZERO
    }
}
```

## 初期配布をゼロにする、の実装

「プレマインなし」を主張するのは簡単ですが、**証明できる形にする**には工夫が要ります。

Orange のジェネシス (ブロック 0) は、**報酬の 10 OAG を誰も使えない支払い条件に縛って発行**します。受け取らないのではなく、焼却する。

```rust
/// ブロック報酬を**焼却する**ジェネシスを定義する。
///
/// 10 OAG は発行されるが、誰にも使えない支払い条件
/// ([`Lock::unspendable`]) に結び付けられる。受け取らない
/// ([`GenesisSpec::without_reward`]) との違いは、**発行された事実が
/// 台帳に残る**ことである。
pub fn with_burned_reward(network: Network, timestamp: i64, message: &[u8]) -> GenesisSpec {
    GenesisSpec {
        network,
        timestamp,
        message: message.to_vec(),
        outputs: vec![TxOutput::new(
            oag_consensus::params::BLOCK_REWARD,
            Lock::unspendable(),
        )],
    }
}
```

受け取らない (出力ゼロ) でも結果は同じですが、焼却だと **UTXO セットに 1 件残り、エクスプローラで `oag1qqqq…` に 10 OAG が置かれたまま見えます**。「誰も取っていない」ことが、主張ではなく表示になる。

# ブラウザのウォレット: wasm の import をゼロにする

ノードが `25565` 番ポートで HTML を配り、ブラウザ上の wasm が鍵を扱います。**鍵はノードを一切通りません。**

ここで問題になったのが乱数です。`chacha20poly1305` が依存する `getrandom` は、wasm 向けに `wasm_js` バックエンドを使うと **`wasm-bindgen` を引き込みます**。そうなると、ビルドにバージョンを合わせた CLI が必要になり、`cargo build` だけでは再現できなくなる。

なので `getrandom` の**カスタムバックエンド**を使いました。

```
RUSTFLAGS='--cfg getrandom_backend="custom"'
```

中身は BLAKE3 の keyed XOF を使った CSPRNG で、**種は起動時に JS 側の `crypto.getRandomValues` から 32 バイト渡します**。

```js
const seed = new Uint8Array(32);
crypto.getRandomValues(seed);
call({ cmd: "seed", bytes: hex(seed) });
seed.fill(0);
```

結果として、**この wasm の import セクションは空**になりました。

```js
WebAssembly.instantiate(bytes, {})   // これで動く
```

import がゼロだと何がうれしいかというと、**ブラウザとの接点が「バイト列を渡す」1 本だけ**になります。glue コードが無いので、読むべき面が小さい。CI に「import が増えていないか」を機械的に確認する検査を入れてあります。

暗号化は Argon2id (m=128 MiB, t=4) で、記録は localStorage に置きます。**パラメータは記録の中に保存**してあるので、後から既定値を上げても古いウォレットは開けます。

## ついでに: wasm のバイト列は再現しない

CI で「置いてある wasm が古くないか」を確認したかったのですが、**ビルドし直してバイト比較する方法は動きません**。

```
$ strings wallet.wasm | grep '/root/.cargo'
/root/.cargo/registry/src/...
```

**cargo のレジストリのパスが焼き込まれます**。手元は `/root/.cargo`、CI は `/home/runner/.cargo` なので、永久に一致しない。secp256k1-sys の C 部分を clang がコンパイルするので、clang のバージョンでも変わります。

なので**原稿のフィンガープリント**で見ることにしました。ソースを 1 行変えるとフィンガープリントがずれることも確認済みです。

# 今どうなっているか

面白かったのが RandomX のシードです。`seed_height()` は

```rust
pub fn seed_height(height: u64) -> u64 {
    if height < SEED_EPOCH_BLOCKS + SEED_LAG {   // 2048 + 64 = 2112
        return 0;
    }
    (height - SEED_LAG) / SEED_EPOCH_BLOCKS * SEED_EPOCH_BLOCKS
}
```

となっていて、**高さ 2112 までは「ブロック 0 のハッシュ」がそのまま RandomX のシード鍵**になります。

つまりチェーンが 2112 に届くまでは、掘っているブロックが全部ジェネシスのハッシュを鍵に計算されている。初めてシードが切り替わるとき、採掘者は **2 GB のデータセットを再構築**するので 1〜2 分止まります。これは故障ではなく仕様です。

`SEED_LAG` を 64 ブロック置いているのは、**浅いリオーグでシードが変わるのを防ぐ**ためです。シードが変われば再構築が要るので、リオーグのたびに採掘が止まってしまう。

## 満杯のブロックはいくら稼ぐのか

発行が終わった後を計算すると、きれいな数字になりました。

```
200,000 バイト × 0.000005 OAG/バイト = 1.00000 OAG
```

最低中継料率を `MAX_BLOCK_SIZE` に掛けると**ちょうど 1 OAG**。ヘッダとコインベースの分を引くと 0.998975 OAG です。

これは現在の報酬 10 OAG のちょうど 10 % です。ただし**これは床であって相場ではありません**。実際の手数料は混雑で決まります。

# バイブコーディングで合意形成のコードを書くということ

11 日で 37,000 行という数字が出ているので、はっきり書きます。**これはバイブコーディングです。**

バイブコーディングは 2025 年 2 月に Andrej Karpathy が言い出した言葉で、**コードが存在することを忘れて AI に任せきる**やり方を指します。私がやったのもそれで、**37,000 行を 1 行ずつ読んではいません。**

## 本来これはかなり危ない

まず前提を置きます。**合意形成のコードをバイブコーディングで書くのは、普通に考えて危ない**です。理由が 3 つあります。

1. **バグが資金の消失に直結する**。Web アプリなら直してデプロイし直せばいいが、ここは直らない
2. **チェーンは巻き戻せない**。間違ったブロックが積まれたら、捨てるか、全員に更新させるしかない
3. **静かに壊れる**。1,844 億 BTC の事故 (CVE-2010-5139) は、**検証を通ってブロックに入りました**。テストが赤くなって気づくのではなく、誰かが気づくまで台帳に残る

なので「AI に書かせたら動いた」では済みません。**出力が正しいかを人間の側で検算できる土台**を先に作る必要がありました。

## 何を土台にしたか

実際にやったのは、この 4 つです。

### 1. 仕様書を 3,101 行、先に書いた

これが一番効きました。**仕様が先にあると、エージェントへの指示が「§10.4 のとおりに実装して」で通る**。曖昧なところでだけ議論が発生し、それは仕様の穴なので、仕様側を直します。

逆に言うと、**仕様が無い状態でバイブコーディングすると、エージェントが勝手に決めた仕様がコードの中に散らばる**。後から読み直したときに「なぜこうなっているのか」が誰にも分からなくなります。

### 2. 後から変えられない決定は、全部自分で決めた

アドレス形式、sighash が何にコミットするか、発行カーブ、タイムスタンプの型、難易度の表現。**これらは一度動き出したら直せない**ので、エージェントに委ねていません。

仕様書に「検討したが採用しなかったもの」の表を置いたのも同じ理由です。判断の履歴が残っていないと、次に同じ議論を一からやることになります。

### 3. テストを 685 本

書いたのはエージェントですが、**何を試すべきかは仕様から出てきます**。「金額の合算が溢れたら弾くこと」は仕様に書いてあるので、それに対応するテストがあるかを確認できる。

```rust
#[test]
fn total_output_uses_checked_arithmetic() { ... }
```

読んでいない 37,000 行のうち、**「壊れたら困る」部分にはテストが張ってある**、という状態を作りました。

### 4. mainnet に出す前に実機で確かめた

ここはエージェントに任せられませんでした。特にブラウザのウォレットは、**友人に別の端末で試してもらって初めて**「受け取り側の走査」が動くことが確認できました。

送る側のコードは自分で何度も試せますが、**受け取る側が入金を見つける経路は、別人の別の端末でしか通りません**。導出パスかアドレス符号化がズレていたら「送れたのに相手に見えない」で終わるところでした。

## 結局どういう分担だったか

| | 誰が |
| --- | --- |
| 後から変えられない決定 | **人間** |
| 仕様書 | **人間** (議論はエージェントと) |
| 実装・テストの記述 | **エージェント** |
| mainnet 前の実機検証 | **人間** |

「AI が全部書いた」でも「自分が全部書いた」でもありません。**決定は人間・記述はエージェント・検証は実機**でした。

## 正直なところ

これは「**バイブコーディングでも安全に書けます**」という話ではありません。**バイブコーディングの出力を検算できる土台を先に作った**、という話です。

そして土台があってもなお、**未検証のものが残っています**。LWMA の窓幅 90 はシミュレーションをしていない暫定値ですし、私が読んでいない 37,000 行の中に何が埋まっているかは、私にも分かりません。

**通貨としての価値がゼロだから、この状態で mainnet を動かせている**だけです。値が付いているものに同じやり方は勧めません。

# まとめ

なぜ fork しなかったのか、をもう一度まとめると、

1. **やりたかったことが定数では表現できなかった**。スクリプトを消すのは心臓の入れ替えで、fork の上でやるより書いたほうが読める
2. **Bitcoin が 17 年で見つけたバグが全部公開されている**。一から書けば、ブロック 1 の前に全部塞げる
3. **仕様書を先に書けば、矛盾は文章の段階で見つかる**。後から変えられない決定が多い領域では、これが一番安い

そしてバイブコーディングの話に引き寄せると、**3 番が 1・2 を可能にしています**。仕様書が先にあったから「§10.4 のとおりに」で指示が通り、地雷を塞いだかどうかを後から確認できる形になった。**仕様の無いバイブコーディングでこれをやったら、何が入っているか誰にも分からない 37,000 行**ができていたと思います。

草コインが溢れているのはそのとおりで、これが何かになる見込みは特にありません。ただ **fork ではなく一から書くと、教科書に載っている地雷を自分の手で 1 つずつ踏まずに済む**というのは、やってみるだけの価値がある経験でした。
